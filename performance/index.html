1. SDK performance

What loads in the browser, what it weighs, and how to measure the impact on a complex multi-step form. Eight copies of the same 70-field KYB form, each with a different set of Amplitude components. Nothing else differs.

Runtime behaviour, from Amplitude's documentation

  • Analytics: events batch in memory and flush via fetch to api2.amplitude.com/2/httpapi. One remote-config call at init; if it takes over 5 seconds the SDK falls back to local config (docs).
  • Session Replay: a full DOM snapshot at init, then DOM diffs. Amplitude's published figures: snapshot 10 to 50 ms on load, under 5 ms per interaction, under 2% CPU, 1 to 10 MB memory per active session, payloads compressed 60 to 80%, compression deferred to idle periods by default, optional web worker (docs). Their own Lighthouse test reported FCP about 0.1 s and LCP about 0.2 s slower with the plugin, snapshot about 64 ms, incremental capture about 11 ms (blog). Uploads go to api-sr.amplitude.com/sessions/v2/track.
  • Deferral option: Session Replay can be added after window.load or in requestIdleCallback, which removes it from page-load metrics entirely at the cost of missing pre-init interactions (docs).
  • Autocapture: no extra download; adds capture-phase listeners for clicks, changes and form submit. Default click rules exclude dead clicks on non-interactive elements to keep volume down (docs).
  • Guides & Surveys: loader then full bundle, plus a config fetch from gs.amplitude.com. The bundle dominates the "everything" variant.

How to measure it on a complex form

  1. WebPageTest, cold load. Run each variant URL with the same location, browser and connection profile (for example Sydney, Chrome, Cable), 3 to 5 runs, first view only. Compare: bytes in, requests, Start Render, LCP, Total Blocking Time, and the filmstrip. Expect the baseline and the analytics-only pages to be close; Session Replay and Guides & Surveys add visible download time on slow connections.
  2. Lighthouse Timespan, during interaction. Page-load metrics miss what matters for a long form: typing, validation and step changes. Start a timespan, fill one step, press Continue, stop. Compare TBT and INP across variants. This is where Session Replay's mutation processing shows up.
  3. Chrome Performance panel, main-thread attribution. Record one step of the form and filter by script URL to see exactly how many milliseconds belong to each Amplitude file versus the page.
  4. Field data. Autocapture's Web Vitals event ships LCP, INP, CLS, FCP and TTFB per page view, so once the SDK is live you can compare INP on the form by variant or tenant inside Amplitude itself (docs).
  5. Network cost per session. Fill the whole form on the Session Replay variant with DevTools open, filter by api-sr, and read the total bytes. On the masking page you can see the payloads decoded.
The in-page panel is a convenience. It reports what the browser exposes: resource durations, long tasks, Web Vitals and the moment the SDK's init promise resolved. Transfer sizes are hidden for cross-origin scripts without a Timing-Allow-Origin header, which is why the panel falls back to the measured table above.

What we'd recommend MVSI deploys

  • Analytics with Autocapture everywhere: one 67 kB file, and all field-level friction signals come from it.
  • Session Replay sampled, or targeted at sessions that hit validation errors or abandon a step, rather than 100%. Defer it to idle if load metrics are contractual.
  • Guides & Surveys only on pages that use them. Load it on demand.
  • Pin versions with the npm package (@amplitude/unified) rather than the auto-updating CDN script if change control matters to MVSI's clients.
