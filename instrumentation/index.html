5. Form instrumentation

A manageable event model for hundreds of fields across many interlocking forms, built in MVSI's form engine once rather than in each tenant's form. Starts with Autocapture, grows into precise instrumentation as the team learns what questions it asks, and never collects a field value.

The design constraint

MVSI's situation differs from a product team instrumenting one checkout. There are hundreds of fields, many forms, forms that branch into other forms, and many tenants, each with their own configuration. Field-by-field tracking code does not scale and would be impossible to govern. What does scale is the fact that MVSI renders every form from configuration: the renderer is the single place that knows every field's identity, type, step, validation state and timing. Instrument the renderer and every tenant form is instrumented.

The second constraint is privacy. Friction analysis needs to know that a field was changed, corrected, left blank or failed validation, and how long it took. It never needs the value. The model below has no property that can carry a value, and Amplitude Data's schema enforcement can reject any that appears.

Turn on Browser SDK 2 Autocapture with form and element interactions. For a form built from <form>, <input>, <select> and <textarea> this already gives:

The autocapture variant of the KYB form is instrumented exactly this way.

Where it runs out: Autocapture cannot see validation errors, cannot time how long a field took, does not know which step a field belongs to in a single-URL wizard, and element IDs are only as good as the renderer makes them.

Phase 2: a small, fixed event model in the form engine

Eight events, one set of shared properties, implemented once in MVSI's renderer. Every property is an identifier, a count, a duration or a category. None is free text from the applicant.

That is one track() call per event type in the renderer, parameterised by field metadata it already holds. The KYB form on this site implements the step and validation events in about 20 lines (see kyb-form.js).

Why not one event per field?

Hundreds of fields as hundreds of event names makes the tracking plan unmanageable and every chart a hunt. One Field Validation Failed event with field_id as a property gives a single chart, grouped by field, that ranks every field across every form by failure rate, and a single funnel template that works for any form by filtering on form_id.

Governance at scale

  • One tracking plan in Amplitude Data for the form engine, owned by MVSI. Schema setting: reject unplanned properties, so a stray value property is dropped on ingest rather than stored. Require team review for changes to main.
  • Field identity comes from form configuration, not from labels, and is the same identifier used in Session Replay selector overrides (data-field) and in Autocapture's Element ID. One identifier, three systems.
  • Sensitive flag in configuration. Fields marked sensitive in MVSI's form config get data-sensitive in the DOM, which the central mask selector targets, and is_sensitive: true in events, which lets analysts exclude them from any text-based analysis.
  • Tenancy. Start with one project and tenant_id as a group. Split a tenant into its own project only when it needs separate access control or its own masking rules.
  • Autocapture stays on as the safety net for anything the renderer does not cover, with a page URL exclude list for any admin or internal pages.

Phase 3: what to add once the basics are stable

  • Server-side Application Decisioned events (approved, referred, declined, with reason codes) via the HTTP API, keyed by application_id, so front-end friction can be read against outcomes.
  • Guides & Surveys targeted at fields with high failure rates: inline help on the field, or a one-question survey on abandonment.
  • Experiments on form structure (step order, grouping, help text) with Form Submitted as the primary metric and Field Validation Failed as a guardrail.
  • Session Replay targeted capture rules: record only sessions that fail validation twice or abandon a step, which concentrates the replay quota on the sessions worth watching.
Summary for the proof of concept: enable Autocapture on one tenant's onboarding form, add the eight-event model to the renderer behind a flag, build the funnel and the validation-failure chart, and confirm by network inspection that no payload ever carries a field value. That is a two-week scope with a clear success measure.
