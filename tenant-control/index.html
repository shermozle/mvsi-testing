3. Control across tenants

Can MVSI centrally enforce masking so a client's developers cannot accidentally expose a sensitive field? Yes, for Session Replay masking and for Autocapture scope. This page is deliberately misconfigured to show it.

What this page's code asks for: defaultMaskLevel: "" and unmaskSelector: ["[data-sensitive]"], which would send the TFN, licence and card fields in clear. What the project enforces: shown live on the right, fetched from sr-client-cfg.amplitude.com. When they conflict, the project wins (docs).

What MVSI can enforce centrally, and what stays with each tenant's build

ConcernSupported central control (Amplitude settings, no tenant code change)Implementation responsibility (MVSI or tenant code)
Replay masking levelProject-level Light / Medium / Conservative in Settings → Organizational Settings → Session Replay Settings. Overrides the SDK's defaultMaskLevel when remote config is on. Changes take effect on the next page load; no deploy.Keep remote config enabled (it is the default). Do not set configServerUrl to anything but Amplitude or MVSI's own proxy.
Per-element mask / unmask / excludeCSS-selector overrides in the same settings page. A UI "mask" beats an SDK "unmask" for the same element.Give sensitive fields a stable hook the selectors can target, for example data-sensitive or a class set by MVSI's form renderer, so one central rule covers every tenant form.
Fail-closed behaviourIf remote config cannot be fetched, Session Replay records nothing. Built in.Allow sr-client-cfg.amplitude.com in tenant CSPs, or proxy it. A blocked config call means no replays, not unmasked replays.
Sample rate and quotaProject-level sample rate, dynamic sampling, targeted capture; organisation-wide quota.Nothing, unless a tenant wants a lower rate than the project's.
Which pages recordTargeted Replay Capture by URL, event or property. URL-pattern mask levels (urlMaskLevels) are an SDK option today.Call amplitude.remove("sessionReplayTracking") before restricted areas if a tenant needs a hard stop in code.
Autocapture scopeData → Settings → Autocapture: turn categories on or off remotely, element allow-lists, page URL exclude and allow lists, regex masking patterns. "On" and "Off" override local SDK config; "Default" leaves it alone. Takes effect within about 10 minutes.Keep fetchRemoteConfig on (default since 2.16.1). Autocapture never collects input values regardless of settings; this governs element text and which pages are tracked.
Attribute values in replaysNone. Masking covers text and inputs, not value, placeholder, title, alt, aria-label or data-* attributes.MVSI's renderer must not put applicant data into attributes. Use blockSelector or .amp-block for widgets that do.
URLs containing identifiersNone today in the UI.ugcFilterRules in SDK config to rewrite, for example, /applications/12345 to /applications/*.
Custom event propertiesAmplitude Data schema: block or drop unplanned properties on ingest, require tracking-plan review before changes to main.Never put a field value in an event property. The instrumentation proposal is built around that rule.
Who can change the rulesAdmins and managers on the project. Enterprise RBAC can restrict Data settings to admins; each tenant can be its own project with its own settings if isolation is needed.Decide the project topology: one project per tenant (settings and data isolated, each tenant's rules set by MVSI) or one shared project with tenant_id as a property.
The honest limit: central settings control what the Amplitude SDK does, assuming the tenant actually loads Amplitude's SDK with remote config reachable. A tenant that strips the SDK, blocks the config endpoint or renders PII into HTML attributes is outside what any vendor setting can fix. Those belong in MVSI's platform contract with its clients, and in MVSI's shared form renderer rather than in each tenant's codebase.
